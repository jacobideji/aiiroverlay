# Findings and corrections

Everything the Offensive Lens found in the AI IR Overlay, what was wrong with it, what replaced it, and what now stops the correction from quietly becoming wrong again.

The fourth column is the one that matters. A correction that nothing guards is a correction with a shelf life: the next refactor, the next release, the next contributor who does not know why a line is there. Every row below names an executable guard, and every guard runs in CI.

## Specification

| What was wrong | Why it was wrong | Correction | Why it is right, and what keeps it right |
|---|---|---|---|
| **M5 Controlled Re-Enable** validated retrieval policies and corpora versions, and never mentioned memory state. | Memory is written by the agent *during* the incident and carries instructions, not only facts. An entry written before containment executes on the first turn after re-enable. Corpora validation inspects a different artifact; harness replay re-runs the trigger rather than the agent's own stored state. The sequence could complete in full with the cause still present. | Six steps. New step 3 diffs the containment snapshot against the last pre-incident baseline, removes what the incident wrote, and retains the snapshot as evidence rather than as a restore source. M1 gains the operational check that captures the snapshot, on the first transition out of M0 whichever mode that is. A prerequisite note states what happens where no baseline exists. | Right because it closes the only re-entry path the other five steps cannot reach, and it separates the two artifacts that were conflated: evidence and restore source. Kept right by the fixture's **`spec-m5` profile**, which implements M5 exactly as first published and is hardened in every other respect. It fails exactly `OL-T204` and `OL-T401` and must continue to. If the memory step is ever removed or weakened, `spec-m5` and `hardened` converge and the fixture reports it as a blind probe. |
| The M5 sequence was restated in full in **PB01, PB14 and PB18**, none carrying the memory step. | Fixing only the canonical copy would have left three documents instructing responders to skip the step. The playbooks were not at fault: they were faithfully restating a specification that was incomplete. | The step inserted into all three sequences and the lists renumbered. PB18's back-reference to "the replay step (3)" corrected to (4). | Right because a canonical fix that does not reach its restatements is half a fix. Kept right by a **`RELEASE_CHECKLIST.md` pre-flight gate** added in the same release: when a mode, an MVO control or an evidence class changes, confirm the affected lens still covers it. The repository's existing cross-reference existence check covers the renumbering. |
| The canonical definition of MVO-4 in `framework/01-minimum-viable-overlay.md` still carried the five-step sequence after the memory step was added to `kill-switches/overview.md` and to three playbooks. | The propagation sweep was scoped to `playbooks/`. But `framework/01` is where the control is *defined*, so it outranks every restatement of it: a reader entering through the framework core received the sequence G2 was raised against, and the core and the mode specification asserted different things about the same control. | Six steps, in the mode specification's order, with memory validation between policy validation and harness replay. | Right because the definition of a control cannot say less than the specification of the mode that implements it. Kept right by a detector rather than by memory: any ordered list of four or more items containing a read-only re-entry, a harness replay, an incremental re-enable and a return to normal is a restatement of this sequence, and one without a memory step is a finding. Twelve such lists exist in the repository. Eight lacked the step; the four that still do are documented exclusions rather than oversights. |
| **PB06, PB07 and PB12** rate Memory Snapshot as high-value evidence in their own tables, then omitted memory from their recovery sequences. | A playbook that names an evidence class high-value for its scenario and then never validates it on the way back out contradicts itself. Injection persists as an instruction; a retired credential can sit in memory where rotation does not reach it; shared memory carries an insider's framing of what is permitted. | One step each, stating the scenario-specific reason rather than repeating the generic one, inserted above the point every existing numeric back-reference in those files targets. | Right because the test is the playbook's own evidence rating, not an outside judgement about scope. That is also why PB03, PB08 and PB10 are untouched: all three rate the class lower, and PB10 states that vendor memory is not customer-visible, which matches `SCOPE-AND-ETHICS.md`. Kept right by the same mechanical comparison: class D severity against the presence of a memory step in the recovery sequence. |

## Reference implementation

| What was wrong | Why it was wrong | Correction | Why it is right, and what keeps it right |
|---|---|---|---|
| `activate(M3, scope=None)` reset the whole registry before the probe ran, then failed the probe, leaving `current_mode` reporting the previous mode while every write tool was callable. | `_apply_mode()` ran before `probe()`, and the M3 branch re-enabled every tool before applying scope. The contract promised that `effective_at` is set only after a passing probe, but the registry honored no such rule, so a failed activation silently lifted containment while the API reported it in force. | An empty M3 scope is rejected at `activate()` before the registry is touched. Activation snapshots each tool's state and rolls back when the probe does not pass. | Right because the registry now honors the rule the contract already stated, and the rollback closes the whole class rather than the M3 instance. Kept right by **`OL-T201`**, which asserts both that the refusal happens and that containment survives it, and by the fixture's three profiles, which prove the probe can tell a lifted control from a held one. |
| `activate(M3, scope=["<mistyped tool>"])` returned `probe_result='pass'` with `effective_at` set and every write tool still callable. | `probe(M3)` skipped scope entries absent from the registry rather than failing on them, so a scope that resolved to nothing verified as containment. A typo produced verified containment with full write capability. | Unresolvable scope entries are rejected at `activate()`. `probe(M3)` treats a name that does not resolve as a failed probe rather than a skipped iteration. | Right because a verification step that skips what it cannot find is not verifying. Kept right by **`OL-T201`**'s scope check, which runs a deliberately mistyped tool name on every CI run and requires a `ValueError`. |
| `Mode.M5` was declared and present in `ALL_MODES` but could never become effective. | `_apply_mode()` had no M5 branch and `probe()` fell through to `return False`. MVO control 4 *is* M5, and the framework's pre-production requirements call for all six modes implemented and drilled, so the reference implementation demonstrated five of the six it claimed. | An apply branch and a probe branch for M5, a `ReEnableGate` recording steps 1 to 5 including memory validation, and a `deactivate()` that refuses a direct M4 to M0. | Right because the mode the fourth control rests on is now reachable and gated. Kept right by **`OL-T404`**, which exercises the gate positively as well as negatively: incomplete gate refused, insufficient approver authority refused, fully gated return permitted. A gate that refuses everything would pass a negative-only test and fail this one. |
| `deactivate()` returned M4 to M0 in one call, re-enabling every tool, gated on nothing but actor inequality. | M4's exit criteria are eradication complete, then M5. Returning straight to M0 skipped every validation step, and actor inequality is separation of duties, which is necessary but not sufficient: any differing actor qualified, with no authority level checked. | Direct M4 to M0 refused. Returning from M5 requires a complete `ReEnableGate` and an approver holding CISO or Incident Commander authority. | Right because it enforces what the ladder already specified. Kept right by **`OL-T404`** and **`OL-T405`**, which separate the two concerns: independence is checked at every mode, authority only at M5, which is what the ladder says and what Tier-1 SOC ownership of M1 to M3 requires. |
| Tool calls produced no evidence. A denied invocation returned `'denied'` to the caller and was recorded nowhere. | `activation_history` held mode transitions only. Every containment verdict against the implementation was therefore unevidenceable from its own logs: the control could work and nothing in the artifact could show it. | A `ToolCall` record carrying tool, params, agent, mode, timestamp, caller correlation id and the `activation_id` of the containment decision in force. Opened **before** dispatch with the outcome written back, inside `Tool.call()` via a recorder the API wires up. | Right on two counts. Opening the record before dispatch captures denials, queued calls and retries, which a success-path log never sees, and leaves a record even when a call dies mid-dispatch. Placing it inside `Tool.call()` rather than in a wrapper means no existing call site can bypass evidence by forgetting a new entry point. Kept right by **`OL-T302`**, which induces all three outcomes and requires a record with six fields for each. |
| M2 marked write tools `requires_approval` and returned `'queued'`, but no `approve` or `deny` method existed. | A queued call could never be approved, executed or denied. M2's own operational check, that the approver has authority to deny, was unsatisfiable by construction: the queue was a denial with a friendlier word. | A held call is retained with an `approval_id`. `approve()` releases exactly that call, `deny()` refuses it, one decision per id with no bulk approve. The agent's own identity is refused as approver. Every decision is audited with approver, timestamp and reason, and `approval_metrics()` exposes pending, approved and denied counts. | Right because the gate can now refuse, which is the only property that makes it a gate. An approver may release a held call but may not un-contain a tool: a disabled tool stays denied on the approved path, so M2 approval cannot be used to defeat M1 or M3. Kept right by **`OL-T209`**, which treats a denial rate of zero across a window as PARTIAL rather than PASS, so a gate that exists and is never exercised is reported rather than credited. |
| `Activation` recorded mode and scope but never the resulting registry state. | Mode and scope describe what was *requested*. Answering "what could this agent do at 02:14?" from mode alone requires assuming the apply logic was correct, which is the thing under investigation, and which `OL-T201` had just shown could be wrong. | `ConfigSnapshot` captures the effective registry on every state change: activation, rollback and deactivation. `configuration_at(timestamp)` reconstructs a past moment. | Right because it replaces an inference with evidence, and the inference it replaces was demonstrably unsafe. Kept right by **`OL-T305`**, which reconstructs a moment during M1 and asserts that no write tool was callable and reads were live, rather than merely checking that a snapshot exists. |

## What guards the guards

Every correction above is held by a technique, and every technique is held by the lens's fixture, which runs 24 probes against three profiles of the same deployment: control absent, control holding unevidenced, control holding and recorded. A probe that returns the same verdict against all three is **blind**, and the runner fails the build for it.

That is what stops the guards themselves from rotting into decoration. A regression test that cannot fail is not a regression test, and the fixture is the thing that notices.

Not every correction is held that way, and the table above should not be read as
if it were. Six of the rows are documentation agreeing with documentation, and
what holds them is a detector rather than a probe: a search for restatements of a
numbered sequence, a comparison of each `(step N)` claim against the sequence it
cites, a comparison of an evidence class's severity against whether recovery
validates it. These run over text, not over a deployment. They are weaker than a
failing test and stronger than remembering.

Those six are also the clearest instance of the limit below. The propagation sweep
that closed G2 was scoped to `playbooks/`, and the release gate was worded the
same way, so neither could see that the file *defining* the control still carried
the old sequence. The lens found it on the next read-through, which is the method
working, one release later than it should have.

The known limit, recorded in [VALIDATION.md](VALIDATION.md): the lens was written by reading the framework, so it inherits the framework's blind spots. Everything above is guarded. Nothing above can tell you what was never modeled.
