# Crosswalk — NIST SP 800-61r3 → AI IR Overlay

**Source.** *NIST SP 800-61r3, Incident Response Recommendations and Considerations for Cybersecurity Risk Management: A CSF 2.0 Community Profile*, April 2025, by Alex Nelson, Sanjay Rekhi, Murugiah Souppaya and Karen Scarfone. Subcategory text is quoted from the NIST CSF 2.0 Reference Tool export. Neither is reproduced beyond the Subcategory statements: **read this crosswalk with r3 open**, because r3's per-Subcategory Recommendations and Considerations are the normative content and are not restated here.

## What r3 is, and what this crosswalk is for

SP 800-61r3 is not a revision of the r2 lifecycle. It is a **CSF 2.0 Community Profile**: it restructures incident response around the six CSF 2.0 Functions and presents the familiar four-phase model only once, in a table headed *Previous Incident Response Life Cycle Model Phase*, mapped to the Functions that replace it.

r3's model has three tiers. **Govern, Identify and Protect** are preparation, and r3 states they are *not part of the incident response itself*. **Detect, Respond and Recover** are incident response. **Identify's Improvement Category (ID.IM)** is continuous improvement, fed from every Function.

This crosswalk covers the middle tier only: the **32 Subcategories in r3's Table 3, *CSF 2.0 Community Profile part 2: Incident Response***. The preparation tier is already mapped in [`nist-csf-2.md`](nist-csf-2.md) at Function and Category level, and is not re-mapped here.

r3 tells an organization what incident-response outcome to achieve. The overlay tells it **how that outcome is achieved when the actor is an authorized agent**. Where the answer is unchanged by an agent's presence, the row says so.

## DETECT (DE) — 11 Subcategories

r3: *"Possible cybersecurity attacks and compromises are found and analyzed."* For an agent the difficulty is that misuse looks like use, so every row below moves the monitoring target from the host to the agent's action surface.

| r3 Subcategory | Subcategory text | What the overlay adds for agents | Artifact |
|---|---|---|---|
| `DE.CM-01` | Networks and network services are monitored to find potentially adverse events | Network monitoring sees API calls to a model endpoint, not the agent's decisions. The overlay monitors the agent's own action surface instead. | PB11 Family 1 tool-call anomalies · AI-BOM `tools` |
| `DE.CM-02` | The physical environment is monitored to find potentially adverse events | No agent-specific extension. Physical monitoring is unchanged by an agent's presence. | — covered by the existing programme |
| `DE.CM-03` | Personnel activity and technology usage are monitored to find potentially adverse events | The agent is a principal, not a person. Its activity needs the same scrutiny as personnel activity, against a declared baseline. | AI-BOM · Agent Privilege Matrix · PB01 |
| `DE.CM-06` | External service provider activities and services are monitored to find potentially adverse events | A vendor-managed copilot is an external service whose containment granularity the customer does not control, so it is monitored against a contracted evidence SLA. | PB10 · AI-BOM `notes` vendor constraint |
| `DE.CM-09` | Computing hardware and software, runtime environments, and their data are monitored to find potentially adverse events | Runtime for an agent includes its system prompt, tool definitions, retrieval corpus and memory. All four drift without a deploy. | Type E config snapshot · PB22 · OL-T305, OL-T105 |
| `DE.AE-02` | Potentially adverse events are analyzed to better understand associated activities | Adverse events for an agent are authorized actions in anomalous shape, so analysis works on three signal families rather than on malware behaviour. | PB11 Families 1-3 |
| `DE.AE-03` | Information is correlated from multiple sources | Correlation must join the agent's tool-call ledger to downstream SaaS audit logs, because the agent's action and its effect are recorded in different systems. | Type B + Type F · `correlation_id` · OL-T306 |
| `DE.AE-04` | The estimated impact and scope of adverse events are understood | Scope for an agent is bounded by effective tool scope at the time of the event, not by host count. | Agent Privilege Matrix · OL-T102 effective-scope inflation |
| `DE.AE-06` | Information on adverse events is provided to authorized staff and tools | The responder needs the agent's prompts, retrievals and denied calls, and must be able to tell adversary-authored content from system output. | Types A, B, C · OL-T307 evidence poisoning |
| `DE.AE-07` | Cyber threat intelligence and other contextual information are integrated into the analysis | Transferable indicators received from peers enter here: a shared corpus document identity becomes a corpus check. | TI-1..TI-6 · PB11 |
| `DE.AE-08` | Incidents are declared when adverse events meet the defined incident criteria | An agent incident is declared on the Six Triage Questions, which establish capability before impact. | `triage/six-questions.md` · RESPONSE-START.md |

## RESPOND (RS) — 13 Subcategories

r3: *"Actions regarding a detected cybersecurity incident are taken."* r3 states that *"Containment refers to preventing the expansion of an incident"* and that *"Eradication refers to mitigating an incident's effects."* Both are harder for an agent, because the expansion path is a delegation and the effect may persist in a corpus or a memory store that containment never touches.

| r3 Subcategory | Subcategory text | What the overlay adds for agents | Artifact |
|---|---|---|---|
| `RS.MA-01` | The incident response plan is executed in coordination with relevant third parties once an incident is declared | The plan names a mode to enter, not just a team to page, and names who may authorise it. | Kill-switch ladder M0-M5 · PB01 decision log |
| `RS.MA-02` | Incident reports are triaged and validated | Triage validates what the agent *could* do before what it *did*, because an authorized action looks like use. | Six Triage Questions Q1-Q3 · OL-T101 |
| `RS.MA-03` | Incidents are categorized and prioritized | Categorisation is by agent capability class and blast radius rather than by malware family. | PB08 blast radius · Agent Privilege Matrix tiers |
| `RS.MA-04` | Incidents are escalated or elevated as needed | Escalation is a mode transition up the ladder with a stated authority at each step. | M0-M5 · M5 requires CISO/IC · OL-T405 self-approved re-enable |
| `RS.MA-05` | The criteria for initiating incident recovery are applied | Recovery begins only when containment is validated, not when it is merely activated. | MVO-4 entry condition · OL-T201, OL-T207 |
| `RS.AN-03` | Analysis is performed to establish what has taken place during an incident and the root cause of the incident | Root cause for an agent is usually an instruction or a document, not a vulnerability, so analysis reaches prompts, retrievals and memory. | Types A, C, D · PB06 · PB03 |
| `RS.AN-06` | Actions performed during an investigation are recorded, and the records' integrity and provenance are preserved | Actions include the agent's own, and a denied invocation is a recorded action because it is evidence of intent. | Type B incl. denied calls · export manifest `sha256_hash` · OL-T302 |
| `RS.AN-07` | Incident data and metadata are collected, and their integrity and provenance are preserved | Six agent-specific evidence classes, captured in an order that does not destroy them, exportable in 60 minutes. | Types A-F · capture order · evidence-export.spec.md · OL-T301..T308 |
| `RS.AN-08` | An incident's magnitude is estimated and validated | Magnitude includes trust impact, which traditional CIA understates for an agent acting as a trusted party. | CIA+T · PB05 · PB24 |
| `RS.CO-02` | Internal and external stakeholders are notified of incidents | Notification must avoid anthropomorphising the agent and avoid premature root-cause or actor attribution. | PB17 forbidden phrases · framework/04 materiality |
| `RS.CO-03` | Information is shared with designated internal and external stakeholders | What can be shared is specified: six indicator classes, with the rule for what stays behind. | Transferable Indicator Set TI-1..TI-6 · PB23 payload tier |
| `RS.MI-01` | Incidents are contained | Containment is a graduated ladder calibrated to the agent's action surface, with a measured activation target, not host isolation. | M0-M5 · TTA <= 10 min · OL-T201, OL-T206, OL-T210 |
| `RS.MI-02` | Incidents are eradicated | Eradication must reach the retrieval corpus and the memory store, which containment does not touch because they are not the agent. | MVO-4 steps 2-3 · OL-T401, OL-T402 |

## RECOVER (RC) — 8 Subcategories

r3: *"Assets and operations affected by a cybersecurity incident are restored."* The overlay's contribution is that restoration of an agent is staged and gated, and that the artifact used to verify integrity is not the artifact captured during containment.

| r3 Subcategory | Subcategory text | What the overlay adds for agents | Artifact |
|---|---|---|---|
| `RC.RP-01` | The recovery portion of the incident response plan is executed once initiated from the incident response process | Recovery is the six-step MVO-4 sequence, entered only from validated containment. | MVO-4 · kill-switches/overview.md M5 |
| `RC.RP-02` | Recovery actions are selected, scoped, prioritized, and performed | Re-enablement is staged: M1 first, then tools incrementally, with a gate at each stage. | MVO-4 steps 1 and 5 · OL-T404 regression gate |
| `RC.RP-03` | The integrity of backups and other restoration assets is verified before using them for restoration | The restoration asset for an agent includes its corpus and its memory snapshot. The containment snapshot is evidence, never a restore source. | MVO-4 step 3 · pre-incident baseline · OL-T401 |
| `RC.RP-04` | Critical mission functions and cybersecurity risk management are considered to establish post-incident operational norms | Order is set by tool tier: Tier-0 capabilities return before Tier-2 write paths. | Agent Privilege Matrix T0/T1/T2 · PB04 |
| `RC.RP-05` | The integrity of restored assets is verified, systems and services are restored, and normal operating status is confirmed | Verification includes replaying the incident against the restored agent in a harness before it returns to production. | MVO-4 step 4 harness replay · OL-T404, OL-T406 |
| `RC.RP-06` | The end of incident recovery is declared based on criteria, and incident-related documentation is completed | Closure requires an approver who is not the operator, and a recorded verdict per mode. | MVO-4 step 6 approval gate · OL-T405 · assessment-report template |
| `RC.CO-03` | Recovery activities and progress in restoring operational capabilities are communicated to designated internal and external stakeholders | Progress is reported as modes exited and capabilities restored, which is legible to a board. | PB24 Board-Ready Scorecard · PB13 six metrics |
| `RC.CO-04` | Public updates on incident recovery are shared using approved methods and messaging | Public messaging follows the same forbidden-phrase discipline as internal notification. | PB17 · PB05 |

## Where the overlay adds nothing

`DE.CM-02` physical-environment monitoring is unchanged by an agent's presence. It is listed rather than omitted so the count stays honest: **31 of the 32 Subcategories carry an agent-specific extension, one does not.**

## What this crosswalk does not claim

- **It is not a conformance mapping.** Satisfying the overlay does not satisfy r3. r3's Subcategories carry Recommendations and Considerations this file does not reproduce, and an organization is accountable to those, not to this table.
- **It does not cover r3's preparation tier.** Govern, Identify and Protect are mapped at Function and Category level in [`nist-csf-2.md`](nist-csf-2.md). r3 itself places them outside incident response.
- **It is a maintainer interpretation**, not a NIST publication, and not reviewed by NIST.
